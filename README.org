#+title: Cyclone V SoC MIPS32

* Overview
This repository contains a MIPS32/R2000-style soft core implemented in VHDL for the Intel Cyclone V SoC on the DE10-Standard board, plus the host-side and HPS-side tooling used to build, program, observe, and test it.

The project is split across three layers:
- FPGA RTL and Quartus project files under ~fpga/~.
- HPS user-space utilities under ~software/~ that access FPGA peripherals through the lightweight HPS-to-FPGA AXI bridge.
- Support scripts and sample assembly programs under ~scripts/~.

The repository also contains presentation material under ~presentation/~ and a large number of Quartus/ModelSim generated artifacts under ~fpga/~.

** Important Directories
- ~fpga/rtl/core/~: datapath and control building blocks such as the ALU, register file, PC, muxes, sign extension, branch support, and FIFO logic.
- ~fpga/rtl/mips_32.vhd~: top-level integration of the FPGA fabric with the Cyclone V HPS-facing system.
- ~fpga/tb/~: ModelSim testbenches and simulation Makefile.
- ~software/led_test/~: simplest HPS-to-FPGA memory-mapped I/O smoke test.
- ~software/bram_test/~: BRAM access test from Linux user space.
- ~software/fibonacci/~: loader and readback utilities for running a sample Fibonacci program on the soft core.
- ~software/flasher/~: instruction-memory programming utility that consumes a generated ~program.hex~ file.
- ~software/hps_lcd/~: ARM cross-compiled LCD monitor/debugger application for the DE10-Standard LCD.
- ~software/read_test/~: simple memory-mapped inspection utility for PC, write-info, instruction memory, and data memory.
- ~scripts/assembler.py~: custom assembler for the instruction subset used in this repo.
- ~scripts/fibo.asm~: sample assembly program used by the flasher flow.

* Supported Instruction Subset
The current software toolchain in this repository supports the instruction subset implemented by the assembler and main control logic:

- R-type: ~add~, ~sub~, ~and~, ~or~, ~slt~
- I-type: ~addi~, ~lw~, ~sw~, ~beq~

Branching loops are expressed with ~beq~, including unconditional branches such as ~beq $0, $0, offset~.

* Prerequisites
You need the following tools available on the development host:

- Intel Quartus Prime for synthesis and programming.
- ModelSim for the VHDL testbenches.
- GTKWave for waveform viewing.
- Python 3 for the assembler script.
- SSH and SCP access to the board.
- Intel SoC EDS or an equivalent ARM cross-toolchain for ~software/hps_lcd/~.

For the LCD application specifically, the build expects an SoC EDS environment with the HPS hardware libraries available. The top-level helper target invokes ~embedded_command_shell.sh~ before running ~make~ in ~software/hps_lcd/~. If you build it manually, exporting ~SOCEDS_ROOT~ is enough:

#+begin_src bash
export SOCEDS_ROOT=~/intelFPGA/20.1/embedded
#+end_src

or an equivalent environment where the Altera HPS hardware libraries are available.

* FPGA Build Flow
Compile the Quartus project from the repository root:

#+begin_src bash
make fpga-build
#+end_src

This runs:

#+begin_src bash
cd fpga && quartus_sh -t build.tcl
#+end_src

The ~build.tcl~ script opens the ~mips_32~ Quartus project and performs a full compile flow including synthesis, fitter, assembler, and timing analysis.

To program the FPGA fabric:

#+begin_src bash
make fpga-flash
#+end_src

** JTAG Device Selection
The Cyclone V uses a daisy-chain JTAG configuration. In the Quartus Programmer, ignore the ~SOCVHPS~ device and program only the FPGA fabric device with the generated ~.sof~ file. The provided Make target uses device index 2:

#+begin_src bash
quartus_pgm -m jtag -c 1 -o "p;mips_32.sof@2"
#+end_src

* Simulation Flow
Testbenches live under ~fpga/tb/~.

#+begin_src bash
cd fpga/tb
make sim_alu
make sim_alu_ctrl
make sim_register
make sim_pc
make sim_main_ctrl
#+end_src

Each simulation target compiles the required RTL and testbench, runs ModelSim in command-line mode, dumps a ~.vcd~ waveform, and opens it in GTKWave.

To remove generated simulation outputs:

#+begin_src bash
cd fpga/tb && make clean
#+end_src

* Assembly and Program Loading
The assembler converts a restricted MIPS assembly file into a hex image suitable for the flasher utility.

Generate machine code from the sample program:

#+begin_src bash
python3 scripts/assembler.py scripts/fibo.asm -o scripts/program.hex
#+end_src

Or print the assembled words to stdout:

#+begin_src bash
python3 scripts/assembler.py scripts/fibo.asm
#+end_src

Then deploy and run the flasher:

#+begin_src bash
make flasher_deploy
make flasher_run
#+end_src

Or do the complete sample flow in one command:

#+begin_src bash
make flasher_all
#+end_src

* HPS Software Utilities
The HPS-side programs are built around ~scp~, ~ssh~, ~gcc -std=gnu99~, and direct ~mmap()~ access to FPGA-mapped peripherals.

** LED Test
The simplest integration test:

#+begin_src bash
make sw-run
#+end_src

This copies ~software/led_test/led.c~ to the board, compiles it on the target, and runs it.

** BRAM Test
#+begin_src bash
make bram-run
#+end_src

** Fibonacci Loader and Readback
#+begin_src bash
make fibo-run
make fibo-read
#+end_src

** Readback Utility
For direct inspection of the mapped memories and status registers, use the small helper under ~software/read_test/~ as a reference or launch point for custom diagnostics.

** LCD Monitor
The LCD application under ~software/hps_lcd/~ is different from the other utilities:

- It is cross-compiled on the host using ~arm-linux-gnueabihf-gcc~.
- It links against the Altera HPS hardware libraries from SoC EDS.
- It acts as an on-board monitor that reads instruction memory, the current PC/status register, and FIFO-exported values to display live state on the LCD.

Typical flow:

#+begin_src bash
make lcd_build
make lcd_deploy
make lcd_run
#+end_src

The current ~main.c~ maps the following lightweight-bridge offsets:

| Offset | Use |
|--------+-----|
| ~0x0000~ | Data memory window |
| ~0x1000~ | Instruction memory window |
| ~0x2000~ | FIFO valid bits |
| ~0x2010~ | FIFO update counter |
| ~0x2020~ | FIFO slot 2 |
| ~0x2030~ | FIFO slot 1 |
| ~0x2040~ | FIFO slot 0 |
| ~0x2050~ | PC/status PIO |

* Hardware/Software Bridge
Communication between Linux user space on the ARM HPS and FPGA peripherals is performed through the lightweight HPS-to-FPGA AXI bridge.

- Bridge base address: ~0xFF200000~
- Typical access pattern: ~open("/dev/mem")~ + ~mmap()~ + volatile pointers
- Bridge span used by the LCD monitor: ~0x00200000~

This pattern is used throughout the HPS software in ~software/~.

* Board and Network Assumptions
The repo assumes a direct host-to-board Ethernet setup with SSH access to the HPS.

** Host Setup
The host machine is expected to expose network access to the board and define an SSH alias such as:

#+begin_src bash
Host cyclone
    HostName 10.42.0.50
    User root
#+end_src

** Board Setup
The current workflow assumes a static IP on the board. On Angstrom-based systems, that may require bypassing ~connman~ with a dedicated systemd service:

#+begin_src bash
# /etc/systemd/system/eth0-static.service
[Unit]
Description=Force eth0 Static IP
After=network.target

[Service]
Type=oneshot
ExecStart=/sbin/ifconfig eth0 10.42.0.50 netmask 255.255.255.0 up
RemainAfterExit=yes

[Install]
WantedBy=multi-user.target
#+end_src

* HPS SDRAM Pin Assignment Script
When Platform Designer generates the HPS subsystem, it also generates an SDRAM pin-assignment Tcl script under the synthesized SoC output tree:

~fpga/soc_mips/synthesis/submodules/hps_sdram_p0_pin_assignments.tcl~

This script is required to apply the electrical termination settings needed by the Cyclone V HPS DDR3 interface. If those assignments are missing, Quartus fitting can fail with termination-control related errors.

** Run-Once Rule
Do /not/ run that script inside the automated ~build.tcl~ flow. Running it concurrently with compilation can trigger Quartus database locking errors.

Instead, run it manually from the Quartus GUI when:
1. Setting up the project for the first time.
2. Regenerating the ~soc_mips~ Platform Designer system.

After the assignments are written into the project settings, normal command-line builds can continue with ~make fpga-build~.

* Generated Files in This Repository
This workspace includes many generated outputs. The most important ones are:

- ~fpga/db/~ and ~fpga/incremental_db/~: Quartus compilation databases.
- ~fpga/*.sof~, ~fpga/*.rpt~, ~fpga/*.summary~, ~fpga/*.smsg~: Quartus outputs and reports.
- ~fpga/work/~, ~fpga/*.wlf~, ~fpga/*.vcd~: ModelSim and waveform outputs.
- ~scripts/program.hex~: generated machine-code image used by the flasher flow.

These files are useful for local iteration, but the main source code lives under ~fpga/rtl/~, ~fpga/tb/~, ~software/~, and ~scripts/~.

* Quick Start
For a representative end-to-end workflow:

1. Run the HPS SDRAM pin-assignment Tcl script once if this is a fresh Quartus setup.
2. Build the FPGA image with ~make fpga-build~.
3. Program the board with ~make fpga-flash~.
4. Assemble and flash the sample MIPS program with ~make flasher_all~.
5. Inspect runtime behavior with one of the HPS utilities, for example ~make fibo-read~ or the LCD flow ~make lcd_run~.
